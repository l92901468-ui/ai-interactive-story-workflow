# 编剧反馈闭环

生成只是半条链路。另外半条是：编剧看了、改了、说了，系统怎么消化。

## 一、为什么不能直接「看到差分就调权重」

AI 稿和编剧改稿之间的每一行差异，都可能有完全不同的成因：

- 召回压根没把该给的资料找出来；
- 概述被理解歪了，或者被扩写了；
- 事件该谁做、按什么顺序做、阻力在哪，设计本身就错了；
- 决策是对的，只是写出来不对味。

把「哪里改了」等同于「哪里错了」，然后直接调权重，是最容易出错的一步。权重一旦被错误的归因污染，后面每一轮都会偏，而且很难发现是从哪一轮开始偏的。

所以这里把两件事分开：**差分只负责记录哪里变了，归因由人工给出。**

## 二、三种输入形态

编剧可能给这三种东西，系统在「改进权重和路径」这件事上对它们一视同仁，都是来源：

| 形态 | 额外作用 |
|---|---|
| 只给好坏（`verdict`） | — |
| 详细意见（`comment`） | — |
| 直接给改好的文章（`revision`） | **额外入库**，成为下一轮的知识库语料 |

改好的文章进知识库时分两个槽：正文进 `style`，承接关系进 `continuity`。概述单独留在 `planning`，不会跟文风槽串——这是「来源隔离」，也是不回退清单的第一项。

## 三、分级生效

| 来源 | 何时生效 |
|---|---|
| 编剧明确写出的意见 | 立即，下一次生成必须装配 |
| 编剧提交的改好正文 | 立即入库 |
| 改稿里附带的明确意见 | 立即 |
| 某条资料该 boost / downrank | 归因后才生效 |
| 某条长期策略 | 归因后才生效 |
| 通用工作流（路径）怎么改 | 提建议，人工研究后再应用 |

## 四、归因

每个差分由人工选定**一个**主要归因层：

| 层 | 含义 |
|---|---|
| `input_retrieval` | 召回或参考路由造成 |
| `overview_interpretation` | 错误理解或扩张概述 |
| `scene_decision` | 事件所有权、顺序、阻力或关系动作设计错误 |
| `prose_realization` | 决策正确，但具体表达失败 |

再选一个结论范围：

| 范围 | 含义 |
|---|---|
| `writer_scene_choice` | 本场选择，只留在场景记录 |
| `project_pattern` | 当前项目中有条件复用 |
| `generalizable_failure` | 可进入通用工作流候选，仍需跨场验证 |

## 五、权重安全门

只有同时满足下面几条，权重才会真的动：

1. 归因层是 `input_retrieval`；
2. 结论范围至少是 `project_pattern`；
3. 单次幅度不超过上限；
4. 被调整的资料确实进了这一次的生成包。

禁用（`avoid`）更重：必须编剧明确禁用，或者有两次独立的负面验证。

不满足时系统不会静默跳过，而是返回被拦下的原因（`blockedBy`），便于人工判断要不要换一种归因。

## 六、路径改进

路径（route）不自动改。系统根据归因的聚集情况生成建议：

```
rp_retrieval_xxxx | insertAfter: retriever → retrievalAuditor | awaiting_human
  理由: 多次归因到召回层，说明召回结果没有被独立复核就进入了起草
```

人工研究哪些地方好、哪些不好之后，确认应用，路径才真正变化，下一次生成就走新路径。

`retrievalAuditor` 和 `proseReviewer` 这两个 agent 默认不在路径里，只有人工确认后才会被插入——它们是路径改进真正落地的地方，否则建议只是一句空话。

## 七、不回退

每应用一次改进，都会重跑累计不回退清单：

来源隔离 · 连续性 · 事件完成度 · 决策所有权 · 失败覆盖 · 变量结算 · 知识边界 · 因果追踪

新增的审核环节最容易把老规则挤掉（比如为了查文风，把来源隔离放松了）。这张清单的作用就是让这种退化当场暴露。

## 八、证据完整度

如果这次生成缺少上下文哈希、计划哈希、草稿哈希、决策链接或召回路由中的任一项，生成记录会标 `evidence_incomplete`。

此时改稿照常采用，但**不得据此推断调权**——不知道当时用了什么资料，就没法判断是资料的问题还是别的问题。
